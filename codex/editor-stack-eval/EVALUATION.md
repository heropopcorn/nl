# heropopcorn/nl 导演台技术方案评估

## 结论

**“用游戏引擎编排场景，再播放并导出镜头”适合这个项目，导演台也应该继续做；现阶段不应改成每个场景都写代码，也不应把编辑器重写成纯 JS、只让 Godot 负责预览。** 推荐把 Godot 保持为场景数据、空间编辑、实时效果和播放的唯一权威实现，先把已有导演台收敛成一个好用的“短镜头编排器”，而不是继续扩成通用游戏编辑器。

但还要纠正一个产品边界：**Godot 很适合生成和播放镜头画面，却不会因为有了场景编辑器就自动变成完整的视频生产工具。** 当前仓库已经解决了不少“搭景和预演”，尚未解决镜头时长、镜头运动、角色出场时序、音频对齐、稳定录制/编码、成品文件下载等“出片闭环”。下一阶段最重要的不是换编辑器技术栈，而是尽快证明一个 10～30 秒镜头可以从搭建、播放到得到可用视频文件。

本结论基于当前工作区实现，而不只基于设计稿：`DirectorDesk` 已有章节/场景、素材抽屉、元素拖放、底图裁片层级、矩形/多边形水域、多角色路线、天气、撤销和本地仓储；本次实际运行 `godot --headless --path . --import --quit` 与 `godot --headless --path . -- --selftest`，结果为 `SELFTEST PASS`。正式站页面本次无法通过检查工具直接打开，因此没有把线上部署是否与当前工作区完全一致作为结论依据。

## 1. “游戏引擎做视频 + 可复用特效”是否合适

这条总思路是合适的，尤其适合目前这种 2D、游戏感、镜头短、场景元素会反复复用的内容。

它的核心收益不是“Godot 能画雨”，而是同一套对象和规则能反复组合：水域有区域、方向和速度；角色有出生点、路线和速度；雨雪、烟花、烟雾可以成为参数化效果；镜头只保存配置，不需要每次重新写一段实现。这样，新增作品主要是在生产数据，而新增一种能力时才写代码。当前仓库的 UV 坐标契约、分区水面材质、角色数组、天气控制器和 JSON schema 已经在朝这个方向走。

Godot 也适合做最终实时渲染。场景编辑与实际播放使用同一份纹理、Shader、粒子、层级和坐标换算，编辑时看到的结果更接近输出结果。官方也把动画、粒子和 Shader 配合 Movie Maker 模式作为离线生成动画/视频的用途之一，可作为后续桌面端稳定导出的技术候选：[Godot Creating movies](https://docs.godotengine.org/en/4.5/tutorials/animation/creating_movies.html)。

需要避免的是把“可复用效果”理解成先造一个很大的特效平台。水、雨已经足以验证抽象；雪、烟花、雾、昼夜都应在出片闭环跑通后按真实脚本需求逐个加入。每种效果都应暴露少量稳定参数，例如区域、方向、强度、开始时间、持续时间，而不是允许用户编写任意逻辑。

## 2. 问题 1：继续做编辑器，还是每个场景用代码摆

**继续做编辑器。每个场景纯代码搭建不应成为主流程。** 代码应该负责扩充“能力”，场景数据应该负责生产“内容”。

原因很直接：本项目预期反复调整背景、元素位置、遮挡层级、水域形状、角色路线和天气。此类工作高度视觉化，参数会频繁试错；如果每次都改 GDScript、运行、观察、再改数值，创作速度会慢，而且只有程序人员能操作。场景数量增加后，代码文件还会混合引擎逻辑与具体内容，复用效果反而变差。

当前投入也已经使“继续编辑器”成为明显优选，而不是沉没成本绑架：

- `DirectorSceneModel` 已有版本化 JSON、校验、未知字段保留、UV 坐标和数量上限。
- `SceneRepository` 已有章节/场景索引、备份、恢复和旧数据迁移。
- `DirectorDesk` 与各控制器已能真实编辑并播放水域、元素和多角色，而不是静态 UI 原型。
- Web 和桌面共用一套交互，素材抽屉已能把内置切片资产拖入画布。
- 自动化自测覆盖了大部分核心数据与播放行为。

只有两类内容适合直接写代码：一是新增一种可复用能力，例如烟花发射器、镜头轨道或新角色控制器；二是一次性的技术演示或难以参数化的特殊镜头。即便是第二类，也应尽量把最终可调参数写回场景数据，而不是复制出“一场景一脚本”。

编辑器也不应继续无边界增长。它应定位为“镜头编排器”，只服务背景、素材摆放、层级、水域、角色、天气、镜头、简单时序和导出。完整 TileMap、任意节点树、脚本编辑、RPG 系统、复杂非线性剪辑都不属于它。

## 3. 问题 2：纯 JS 编辑 + Godot 预览，还是继续全 Godot

**现阶段继续全 Godot；不要拆成“JS 编辑器 + Godot 预览器”。**

纯 JS 的优势主要在表单、列表、响应式布局、文本输入、可访问性、浏览器文件/下载 API 和成熟的前端组件生态。可是这个项目最难的交互不是表单，而是画布上的命中、选中、拖拽、缩放、镜头平移、套索、多边形控制点、层级/Y 排序、角色路线，以及让这些结果和播放画面完全一致。Godot 已经负责这些空间语义。

如果拆成 JS 编辑、Godot 预览，将新增一整套边界：

1. JS 端要重做一套二维画布和交互，或嵌套并操纵 Godot canvas。
2. JS 与 Godot 必须同步场景 schema、坐标、选择状态、撤销、资源 ID、校验错误和播放状态。
3. 每项新能力都要决定在哪一端实现，并测试双端兼容；水域 Shader、脚底锚点和 Y 排序仍只能以 Godot 为最终准绳。
4. 预览差异会变成长期问题：JS 画布看起来正确，不代表 Godot 中纹理锚点、材质、碰撞和相机完全相同。
5. 现有约七千行导演台相关 GDScript、仓储/迁移和自测不能直接消失，重写期会冻结真正的出片能力。

因此，JS 拆分现在不是“把 UI 做方便一点”，而是引入第二套编辑运行时。它只有在产品明确进入“账号、云项目、多人协作、大规模素材管理、审核发布、复杂表格表单”阶段，并且这些网页工作流的价值超过画布交互时，才值得重新评估。

即使未来走混合方案，也建议采用“网页外壳 + Godot 权威画布”，而不是 JS 重写空间编辑：JS 可以负责登录、云资产、项目列表、支付、帮助和下载；Godot 继续负责镜头画布、效果和播放。两端只交换版本化场景命令或完整快照，并保持单一数据契约。

## 4. “Godot 做编辑器不如纯 JS 方便”是不是误区

这是**一半事实、一半归因错误**。

确实不方便的部分包括：复杂表单和长列表的组件选择少于 Web；CSS 式视觉迭代、浏览器响应式布局、富文本、无障碍、输入法细节、剪贴板、文件下载和前端调试生态不如 DOM 直接；运行时工具 UI 也需要自行处理焦点、快捷键冲突和窄屏布局。浏览器端 `user://` 还依赖 IndexedDB，隐私模式、存储权限或清站点数据都可能破坏持久性；Godot 官方 Web 导出文档也明确提示这一点：[Godot Web export](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)。

但下面这些不便不是“必须换 JS”的证据：

- 空间编辑、实时预览、Shader、粒子、角色移动和相机本来就是 Godot 的强项。
- Godot 的 `Control`、锚点和 `Container` 能做自适应工具界面；官方文档也把 Container 定位为复杂、可重排 UI 的基础：[Godot Container](https://docs.godotengine.org/en/stable/classes/class_container.html)。
- 当前 `director_desk.gd` 超过 2600 行，并且大量 UI 由代码即时构建。继续把所有控件、业务状态和画布操作塞在一个脚本里，开发体验自然会越来越差；这是内部模块边界和 UI 组织方式的问题，不完全是引擎能力问题。
- 当前只有背景上传走 Web 文件选择桥接，元素素材仍是硬编码的内置清单。这里感受到的“不灵活”，部分来自资产管线还没产品化，而不是 GDScript 无法实现。

所以正确动作是整理 Godot 内部架构：把章节树、属性面板、素材抽屉、画布工具、播放条拆成独立场景/组件；数据模型和命令操作不直接依赖控件；用 Theme、Container 和可复用属性控件减少手写布局。无需为了获得更好的 UI 工程结构而更换整条技术栈。

## 5. 结合现有投入的推荐路径与可砍范围

### P0 必须坚持

1. **坚持 Godot 单一权威实现。** 保留现有场景 schema、UV 坐标、repository、控制器和自测，不另建 JS 画布。
2. **坚持可视化编排。** 章节/场景、背景、素材抽屉、层级、水域、角色路线、雨和播放是已经成立的骨架；先修可用性和一致性，不推倒重来。
3. **补上最小镜头模型。** 至少定义输出画幅/分辨率、镜头位置与缩放、镜头时长，以及角色开始延迟或路点停留。当前 `camera` 字段只是保留、不执行，所有角色也基本同时开始，仍不足以稳定复现一个导演镜头。
4. **补上最小导出闭环。** 先选择一个可靠主路径并写清限制。建议把桌面 Godot 的确定性逐帧输出/录制作为质量基线，Web 继续承担随开随用的编辑与预览；若必须从 Web 一键录制，再把浏览器录制作为便利出口，而不要把它当唯一母版方案。
5. **把工程导入/导出和备份提到 P0。** 当前 Web 数据位于本站 IndexedDB，不是云存档。只要导演台开始承载真实作品，没有场景包下载与恢复就存在不可接受的数据丢失风险。
6. **补齐用户素材入口或明确产品限制。** 当前素材抽屉只列 `art/sliced/` 的内置资产，背景可上传，但独立透明 PNG 元素尚未形成持久化资产库。如果“增加图片”是核心创作动作，这项应进入 P0。
7. **保留回归测试并新增成片验收。** 除现有 selftest 外，固定一个基准镜头：从空场景开始，10 分钟内完成摆景；重复播放的关键帧位置一致；能导出约定画幅、帧率和时长的文件；重新打开或换设备导入后结果一致。

### P0 可以砍或后做

- 暂不做纯 JS 编辑器，也不做 React/Canvas 双实现。
- 暂不做云端账号、多人协作、在线素材市场和评论审核。
- 暂不做完整时间轴、曲线编辑器、多轨剪辑和转场系统；只做镜头时长、开始延迟、停留等最小时间参数。
- 暂不做章节连续播放。当前“播放当前场景”足以先验证单镜头生产，章节可先承担组织作用。
- 暂不继续堆雪、烟花、雾、昼夜等效果；先让水和雨完整走过保存、播放与导出。
- 暂不做任意节点、任意脚本、完整碰撞/寻路、TileMap 或流体模拟。
- 暂不追求移动端精细编辑；优先保证桌面浏览器的鼠标键盘流程。
- 暂不打磨所有素材管理能力；先支持少量内置资产和一个清晰的透明 PNG 导入流程。

### 推荐实施顺序

先用现有导演台完成一个真实的 10～30 秒竖屏镜头，并记录阻塞点；随后只补“镜头/时序、用户资产、项目备份、导出”四项闭环能力；再把水、雨、角色路线抽成统一的可计时效果接口；最后才根据真实作品需求添加雪、烟花或更复杂的镜头。连续完成 3～5 个真实镜头后再评估 UI 痛点，届时才能判断需要内部重构、网页外壳，还是确实需要更大范围的技术栈调整。

## 6. 风险与替代方案

- **最大产品风险是做成“好玩的编辑器”，却仍不能稳定出片。** 用基准镜头和导出验收把重心拉回最终素材。
- **最大工程风险是单体 UI 脚本继续膨胀。** 在不改变技术栈的前提下拆分组件和命令边界，避免每加一个效果都修改同一个大脚本。
- **最大数据风险是 Web 本地存储。** 场景包导出/导入应先于云存档；正式作品不能只留在 IndexedDB。
- **最大兼容风险来自浏览器录制、编解码和 WebGL 性能差异。** Web 适合编辑/预览，质量母版优先走可控制的桌面导出；浏览器输出作为补充。
- **替代方案不是“一场景一代码”。** 如果全 Godot UI 短期仍拖慢进度，可先做更窄的参数面板，或让少量高级参数通过 JSON 导入，而不是重写 JS 编辑器。只有云端业务成为产品主体后，才采用网页外壳加 Godot 画布的混合架构。

## 给用户直接看的结论摘要

1. 你的总方向是对的：用游戏引擎做可复用场景、角色和水雨等效果，很适合持续生产游戏感短视频素材。
2. 有必要继续做编辑器，不建议以后每个场景都用代码摆；代码应负责新增能力，场景本身应保存为可编辑数据。
3. 现阶段应继续全 Godot，而不是重写成 JS 编辑、Godot 预览。
4. 因为最难的是画布坐标、套索、层级、路线、Shader 和播放一致性，拆成 JS 会制造两套实现和长期同步成本。
5. 你觉得 Godot UI 不如纯 JS 顺手并非完全误区，表单、响应式布局、文件下载和浏览器生态确实是 JS 更强。
6. 但当前很多不便也来自导演台脚本过大、UI 全靠代码搭建和资产管线尚未拆分，先重构内部模块比换栈更划算。
7. 仓库现有 V2 不是一次性原型，章节、场景、素材抽屉、水域、多角色、天气、保存和自测都已有可复用基础，本次 selftest 也已通过。
8. 下一步不要急着继续加雪、烟花和更多按钮，先用现有能力完成一个真实的 10～30 秒镜头。
9. P0 最该补的是镜头画幅与相机、最小时序、透明 PNG 用户素材、项目导入导出，以及稳定的视频输出。
10. Web 版适合随开随用地编辑和预览，但作品不能只存在浏览器 IndexedDB 中，场景包备份应尽快完成。
11. 高质量成片建议先以桌面 Godot 的确定性导出作为基线，浏览器一键录制可以后续作为便利入口。
12. 等连续做完 3～5 个真实镜头，再根据实际瓶颈决定是否增加网页外壳；在此之前不值得承担纯 JS 重写成本。
